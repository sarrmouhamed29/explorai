# 0011. Qdrant as the vector store, and isolation in two layers

- Status: Accepted
- Date: 2026-11-01

## Context

Sub-project 3 (RAG) needs a vector index over document chunks: dense vectors for meaning, sparse vectors for exact terms, and a search that combines both. The index must keep the guarantee of sub-project 2: a user never reads another user's text. Until now that guarantee lives in PostgreSQL, as repository filters plus Row-Level Security (ADR [0010](0010-row-level-security-defence-in-depth.md)). Any vector store outside PostgreSQL sits outside those policies.

Two options were realistic. **pgvector** is an extension of the PostgreSQL we already run (the Compose image is already `pgvector/pgvector`): the vectors would live in a table next to `chunks`, the existing RLS policies would filter every search, and there would be no new service. **Qdrant** is a dedicated vector engine with native sparse vectors, server-side hybrid fusion, payload indexes for multi-tenancy and collection aliases.

**pgvector was the recommendation** in the spec discussion, because it keeps one system and lets RLS protect retrieval directly. **The maintainer chose Qdrant**, preferring to learn and show a dedicated vector engine. This ADR records that choice, what it costs, and how isolation is kept despite it.

## Decision

Qdrant (image `qdrant/qdrant:v1.20.0`, port bound to `127.0.0.1`, API key required) holds a **derived** index; PostgreSQL stays the source of truth.

- **One collection per embedding model and dimension**, named `chunks_<model>_<dimension>` (`QdrantIndex.collection_name`, lowercase, other characters replaced by `_`). An alias, `chunks_current`, marks the pipeline's complete live collection (moved after a full indexing pass, pruned by `prune-index`); the API does not search through it but searches the collection of its own configured model. `RagSettings.index_name` is that collection name (its single definition; with the fake provider the model part is `fake_<model>`, `RagSettings.index_model`, so switching `RAG_PROVIDER` from `fake` to `real` starts a new index instead of serving hashed vectors under the real model's name), and `chunk_index_entries` rows are keyed by it, so a model *or* dimension change makes every chunk pending for the new collection.
- **A point** is one chunk: id = the chunk id, a named dense vector (`dense`, cosine), a named sparse vector (`sparse`, with Qdrant's IDF modifier), and a payload of `owner_id` (the user id, or `"public"` for the public corpus), `document_id` and `version_id`. **No text.**
- **`owner_id` is a keyword payload index with `is_tenant=True`**, so Qdrant can organise storage by tenant and filter on it cheaply; `document_id` is indexed too.
- **Hybrid search is one Qdrant query**: two prefetches (50 dense, 50 sparse candidates) fused by reciprocal rank fusion inside Qdrant, keeping 30. The scope filter is passed to each prefetch and to the fusion stage.
- **Re-indexing in the background, serving by own model**: `index-pending` fills the collection of its configured model in the background and switches the alias, in one atomic aliases update, only after a pass leaves nothing pending (the alias marks the pipeline's complete live collection, which `prune-index` prunes). The API does not search through the alias: it searches the collection named by its own `RagSettings.index_name`, so it never compares query vectors of one model with document vectors of another. The pipeline builds the new index without touching what the API serves, and the API flips when its own configured model changes. Deploy order: re-index with the pipelines first, then change the backend's model settings. In Compose that order is not staged by default: both services merge the same `x-rag-environment` list, so changing `RAG_EMBEDDING_MODEL`/`RAG_EMBEDDING_DIMENSION` (or `RAG_PROVIDER`, fake to real, as in `docs/evaluation/rag-baseline.md`) and running `up` switches both at once, and answers are partial until re-indexing finishes. To stage it, pin the backend to the old values in an uncommitted override file passed as a second `-f` (Compose merges `environment` per variable, the later file wins): `services: backend: environment: {RAG_EMBEDDING_MODEL: <old>, RAG_EMBEDDING_DIMENSION: <old>}`; remove the override once the pipeline's alias points at the new collection.
- **Sparse vectors are computed by our own code** (`explorai_ai.sparse`: Unicode word tokens, accents folded, each token hashed to 32 bits with `blake2b`, BM25-style term-frequency weights `tf * (k1 + 1) / (tf + k1)` with `k1 = 1.2`). Qdrant applies the IDF part at query time.

**Isolation is enforced in two independent layers** (three checks in code):

1. **The Qdrant filter.** `explorai_ai.scope.build_scope_filter` is the only function in the repository that builds a Qdrant filter (an AST test fails on `Filter(`, `FieldCondition(`, `MatchAny(` or `MatchValue(` in any other file of `ai/src`, `backend/src` or `pipelines/src`; `index.py` is exempt for its point-id and collection plumbing, and the exemption is by file name, so a file called `index.py` elsewhere would also be skipped). Its owner condition is always present: `owner_id` in `[user, "public"]` for `all`, the user alone for `mine`, `"public"` alone for `public`; a `document_id` adds a second condition, never replaces the first.
2. **The re-read under RLS.** Qdrant returns only ids and scores. `ChunkStore.hydrate` re-reads the texts from PostgreSQL through `ScopedSessions.scoped(user_id)` (role `explorai_app`, RLS policies of migration 0005), with an explicit owner condition in the query as well, and keeps only chunks of the latest canonical `ok` version (the stale-index guard). An id that the filter let through by mistake, or an orphan point of a deleted document, becomes nothing: no row, so no text reaches the prompt.

`backend/tests/integration/test_rag_isolation.py` is written to prove RLS alone: it replaces `build_scope_filter` with a filter that matches everything **and** removes the store's explicit owner condition, then checks that Qdrant did hand user B's chunk ids to the store and that none of B's text reaches the candidates, the prompt or the answer for user A. It also checks each defence on its own (the real filter alone excludes B's points; a raw `SELECT` under A's identity sees none of B's chunk rows). Like every integration suite of this sub-project, it has **not been run yet** (Docker was unresponsive); CI is its first run. Because Qdrant holds no text, even a total failure of layer 1 leaks at most ids and scores, not content.

## Alternatives considered

- **pgvector in the existing PostgreSQL (recommended, not chosen).** RLS would filter vectors directly, a chunk and its vector would be written in one transaction (no derived index, no pending state, no prune), one service fewer in Compose and CI, backups in one place. Limits: hybrid search would be assembled by hand (a full-text query plus a vector query plus fusion in SQL or Python), and filtered approximate search with HNSW has known recall pitfalls when a filter is very selective (the index returns its nearest neighbours, then the filter removes most of them). At the current scale (a few papers per user) none of those limits bites, so the honest summary is: pgvector would have been simpler and fully adequate; Qdrant was chosen for learning and for features we would otherwise build ourselves.
- **One Qdrant collection per user.** Strong separation, but many collections to create and migrate, the public corpus searched separately and merged, and an alias switch per user on a model change.
- **The Qdrant filter alone, with texts in the payload.** One fewer query per question, but a single forgotten or wrong filter would leak text with no safety net. Rejected: it gives up the RLS guarantee of sub-project 2.
- **Qdrant as the source of truth.** Same objection, plus a store we cannot query with SQL or protect with policies.
- **Local FAISS or Chroma.** No access control and no server-side tenancy; isolation would rest on application code alone.
- **A sparse model from Qdrant's FastEmbed (BM25 or SPLADE).** Better tokenisation, but downloaded on first use, which tests, CI and containers would need; our encoder needs nothing.

## Consequences

What the choice costs, stated plainly:

- **A second system.** A Compose service, a CI service container, an API key, a health check and a volume. Snapshots, replication and TLS are left to sub-project 10. The Compose health check (`bash` opening a TCP connection to port 6333, since the image has no `curl` or `wget`) and the image tag have **never run** on this machine (Docker was unresponsive during the whole sub-project); CI is their first run.
- **A re-read on every question.** Hydration is one extra PostgreSQL query per question (at most 30 ids). It is the price of keeping RLS as the safety net.
- **Our own sparse encoder.** 32-bit hashing can collide (two tokens share an index; rare, a slightly wrong keyword score); the tokenizer drops every combining mark (category `Mn`), which over-folds scripts where marks change meaning (Japanese dakuten, Thai and Indic vowel signs); a CJK run without spaces becomes one token, so a short CJK query does not match a longer run; the folding depends on the Python `unicodedata` version. Good enough for English papers and French questions, not a multilingual tokenizer.
- **A derived index to keep in step.** Chunks are pending until `index-pending` embeds them (every 30 seconds); points of older versions, duplicates and deleted documents stay until `prune-index` (hourly) removes them. A stale point is harmless (the re-read drops it) but costs a candidate slot. If the collection of the current index disappears (volume reset), the next pass clears its entries and rebuilds it from PostgreSQL.
- **Model changes need a deploy order.** A model change re-embeds the whole corpus (cost and time at the provider). The pipelines are switched first and the backend only once the new collection is complete; a backend switched first serves a partial collection (`indexed` reads `false` for documents not yet in it). Once the pipelines run the new model, the old collection receives no new chunks and is no longer pruned (stale points stay harmless: every hit is re-read under RLS). The previous collection is never deleted automatically (a manual clean-up for now).
- **Error semantics.** A missing collection (HTTP 404) is treated as an empty corpus (a refusal, logged at warning level), because before the first indexing pass that is exactly the situation; the price is that a misconfigured Qdrant URL can look like an empty corpus. Every other error response, and an unreachable server, raises `RetrievalUnavailable` (the API answers `503`).
- **Shared IDF statistics: a confirmed, low-bandwidth cross-tenant channel.** The sparse vectors use Qdrant's `Modifier.IDF` (`index.py`, `ensure_collection`), and Qdrant computes the document frequencies over the whole collection, whatever the owner filter of the query. Other tenants' documents therefore change the weight of a term in everyone's search. No text, title or id leaks, but term membership does: an attacker uploads one document cut into more than 30 near-identical chunks, one containing a probe term X and the others a term Y whose frequency they control, then asks "X Y" scoped to that document. Whether the X chunk survives into the 30 fused candidates, and at which rank, depends on the IDF of X, so it tells whether another tenant or the public corpus contains X. That is about one bit per few questions, under the limit of 30 questions per hour; with reranking disabled the fused rank is returned more directly, so it leaks more. Accepted for now and documented; the mitigation is planned for the safety sub-project: per-tenant IDF computed client-side, no IDF at all, or per-tenant collections or shard keys.
- **Nothing in Qdrant is secret by itself**, but ids, owner ids and vectors are still data (vectors can leak information about the text they encode, a known research result on embedding inversion). The API key and the `127.0.0.1` binding protect it locally; production hardening is sub-project 10.
